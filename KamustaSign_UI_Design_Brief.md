# KamustaSign (LCSign) — UI Design Brief

> Handoff doc for design work: visual/UX enhancement, not a request to change
> product scope or backend logic. Everything described as "built" below is
> real and working, not a mock — treat it as the baseline to improve, not
> greenfield. If you're proposing something that needs new screens or new
> data, flag it as a proposal in your output rather than assuming it's already
> possible.
>
> Companion doc: `KamustaSign_UI_CRUD_Handoff.md` (project root) covers the
> backend/data/auth architecture in depth. This doc deliberately doesn't
> repeat that — it stays focused on what things look like and how they feel
> to use, and only pulls in backend facts where they constrain a design
> decision (e.g. "this list can be empty," "this is a real video, not a
> mock").

## 1. What this product is and who uses it

KamustaSign (in-app name **LCSign**) is a BSIT capstone project: a real-time
American Sign Language (ASL) interpretation system built for **Liloan
Central School** (Liloan, Bonifacio, Misamis Occidental, Philippines). Three
real, working pieces exist today:

1. **A live ASL translator** — webcam in, recognized letters or words out,
   with speech/text translation into a chosen spoken language.
2. **A classroom system** — teachers post signing assignments, students
   submit and get scored, admins manage accounts and classes.
3. **Peer-to-peer video calling** between students and teachers, with
   live captions generated by the same recognition model running locally on
   each device.

The audience is genuinely mixed: school-age students (some Deaf or hard of
hearing, some hearing and learning ASL), teachers, and school administrators.
Keep that spread in mind — this isn't a single-persona consumer app.
**Accessibility isn't a nice-to-have here, it's close to the point of the
product**, but it has not had a dedicated design pass yet (see Section 6).

## 2. Constraints Design needs to work within

- **React Native + Expo (SDK 56), not web CSS.** Every screen is styled with
  RN's `StyleSheet.create` (a JS object subset of CSS-like properties), not
  Tailwind/CSS/SCSS. Proposals should translate into RN style properties
  (`flexDirection`, `gap`, `borderRadius`, etc.) — most CSS concepts map over,
  but things like CSS grid, `:hover` pseudo-classes (RN uses `onHoverIn`/
  `onHoverOut` handlers instead), and arbitrary web fonts don't work the same
  way.
- **The app targets web, iOS, and Android from one codebase**, but web is
  where all real usage and testing happens right now — the translator and
  video-call screens are explicitly web-only today (they use browser
  `getUserMedia`/`<video>`/`<canvas>` directly, not `expo-camera`). Anything
  proposed for those two screens should assume a desktop/laptop browser as
  the primary target, not a phone.
- **Fonts are pre-loaded, not arbitrary.** Only `Baloo2` (700/600 weight) and
  `Inter` (400/500/600 weight) are loaded via `expo-font` in `App.tsx`. A new
  typeface requires adding an `@expo-google-fonts/*` package and a load-time
  change — mention it as a requirement if you want one, don't assume it's a
  free swap.
- **Available visual-effects libraries:** `expo-blur` (`BlurView` — real
  backdrop blur, works on web via CSS `backdrop-filter` and natively on
  iOS/Android), `expo-linear-gradient`, `react-native-svg` (for icons/logo
  marks). No Lottie, no CSS animation libraries, no Framer Motion — motion
  today is hand-built with RN's built-in `Animated` API.
- **Known layout gotcha:** RN Web flex items default to `min-width: auto`,
  which refuses to shrink a row item below its content's intrinsic width.
  This caused a real bug this session (a video panel pushed a whole card off
  the visible screen). If you're proposing side-by-side/row layouts with
  fixed-size media in them, say so explicitly so `minWidth: 0` gets applied
  where needed.
- **No design tool file exists** (no Figma etc. is referenced anywhere in the
  repo) — the design system currently lives only as code (`src/theme/`) and
  in this document. Screenshots in any conversation this doc came from are
  the most accurate current visual reference.

## 3. Current design system

### 3.1 Color tokens (`src/theme/theme.ts`)

Currently on the **"Violet Dusk"** palette (the 2nd of 4 proposed options,
chosen by the team; a glassmorphism treatment sits on top of these base
tokens — see 3.3). Token *names* have stayed stable across two prior palette
swaps specifically so screens never need to change when the palette does —
new proposals should keep using semantic names like `primaryTeal` rather than
raw hex, even though the current value isn't teal-colored.

| Token | Current value | Role |
|---|---|---|
| `primaryTeal` / `primaryTealDark` / `primaryTealLight` | `#6D28D9` / `#4C1D95` / `#C026D3` | Main brand action color; also the Teacher role accent |
| `accentCoral` / `accentCoralDark` | `#FBBF24` / `#B45309` | Secondary accent, CTA pop color, Student role accent |
| `textOnAccent` | `#402D00` | Label color for text sitting on top of `accentCoral` (buttons, active pills) |
| `adminGray` / `adminGrayLight` | `#5B5568` / `#8B84A0` | Admin role accent — deliberately neutral, distinct from the other two |
| `background` | `#FAF5FF` | Pale lavender base (used behind non-gradient screens) |
| `surface` / `surfaceElevated` | `#FFFFFF` | Flat white cards/surfaces |
| `surfaceMuted` | `#EFE5FB` | Soft violet-tinted surface |
| `success` / `needsPractice` | `#2F9142` / `#DC3545` | Correct/needs-practice feedback — kept palette-independent on purpose (green/red is a universal signal, shouldn't shift with brand color) |
| `textPrimary` / `textSecondary` / `textOnPrimary` | `#1E1033` / `#6B6280` / `#FFFFFF` | Body text on light vs. dark/colored surfaces |
| `border` | `#E4D4F7` | Default hairline border |
| `overlay` | `rgba(30,16,51,0.55)` | Modal/scrim backdrop |
| `focusRing` | `#FBBF24` | Keyboard-focus outline color |
| `disabledSurface` / `disabledText` | `#EDE6F5` / `#A79BB8` | Disabled-state colors |
| `gradientStart` / `gradientMid` / `gradientEnd` | `#2E1065` / `#6D28D9` / `#C026D3` | The hero background gradient (indigo → violet → magenta) |
| `glassTint` / `glassBorder` | `rgba(255,255,255,0.14)` / `rgba(255,255,255,0.35)` | Sheer frosted-glass tint/border (palette-agnostic — doesn't need to change if the palette does) |

Role accent mapping (`App.tsx`): **Student → `accentCoral` (gold)**,
**Teacher → `primaryTeal` (violet)**, **Admin → `adminGray`**. This mapping
shows up throughout auth and dashboards — a screen's accent color tells the
user which role's flow they're in.

### 3.2 Type & spacing scale

- Headings: `Baloo2_700Bold` (main) / `Baloo2_600SemiBold` (secondary) — a
  rounded, friendly display face, used for titles/wordmarks/big numbers.
- Body: `Inter_400Regular` / `_500Medium` / `_600SemiBold`.
- Spacing scale: `xs 4 · sm 8 · md 16 · lg 24 · xl 32 · xxl 48`.
- Corner radii: `sm 8 · md 16 · lg 24 · pill 999`.
- Breakpoints (`useResponsive()` hook): mobile `<768`, tablet `768–1099`,
  desktop `≥1100`.
- **Type sizes are set ad hoc per screen** (each screen's `StyleSheet.create`
  picks its own `fontSize`) rather than drawn from a shared type scale. This
  is a real gap — see Section 6.

### 3.3 The glassmorphism system

Two reusable components (`src/components/GradientBackground.tsx`,
`src/components/GlassCard.tsx`) plus a manual pattern used inline in a few
places:

- **`GradientBackground`** — full-bleed `LinearGradient` using
  `gradientStart/Mid/End`, two variants: `"full"` (all three stops, used on
  hero/marketing-feeling screens) and `"subtle"` (flatter, used behind
  dense/scrollable content like dashboards so long text stays readable).
- **`GlassCard`** — a real frosted panel: `BlurView` + a translucent white
  tint (`glassTint`) + a 1px light border (`glassBorder`), rounded corners,
  `overflow: hidden`. This is "sheer" glass — enough blur/translucency to
  read as glass, used on the translator screens and role-select cards where
  there isn't dense text sitting directly on it.
- **"Frosted" variant (not yet its own component — currently inlined per
  screen)** — the same `BlurView` technique but with a much stronger white
  tint (`rgba(255,255,255,0.6–0.65)` instead of `0.14`), used on the auth
  card and dashboard header/cards, where form labels and lists of text need
  to stay legible over the vivid gradient. **This inconsistency (two
  different tint strengths, defined in two different places, not unified
  into one configurable component) is a real cleanup opportunity** — see
  Section 6.
- Text sitting on glass generally goes light/white
  (`rgba(255,255,255,0.75–0.85)` for secondary text, `colors.textOnPrimary`
  for emphasis) on the sheer variant, and stays dark (`colors.textPrimary`)
  on the frosted variant, since the frosted tint is opaque enough for normal
  dark-on-light contrast.

## 4. Screen-by-screen inventory

For each screen: what it does, current visual treatment, and specific things
worth a design pass. Screens are listed roughly in the order a user
encounters them.

### 4.1 Role Select (`src/screens/RoleSelectScreen.tsx`)

Entry point. Wordmark + tagline, then 4 cards: Student / Teacher / Admin /
"jump straight into the Translator" (no login needed for that last one).
Desktop gets a two-pane split (branded gradient panel + card grid); mobile
is a single scrolling column. Full gradient background, glass role cards.

- The 4th card ("Translator", direct access) visually competes with the 3
  role cards even though it's a fundamentally different action (skip auth
  entirely vs. sign in as a role) — worth a look at whether it should be
  visually separated (e.g. a distinct footer link/button) rather than a 4th
  peer card.
- `HandLandmarkMark` (the hand-skeleton logo) is a hand-coded SVG of 21
  points/connections — functional but has never had an actual logo/brand
  design pass. This is the single most-repeated visual element in the app
  (appears on role select, every auth screen, every dashboard header) and is
  probably the highest-leverage thing to get a real design pass.

### 4.2 Auth flow (`src/screens/auth/*`, shell: `AuthScreenShell.tsx`)

Login, Register, Setup2FA (TOTP authenticator enrollment, skippable),
Verify2FA — all four share one frosted glass card centered on the gradient,
with two soft accent-colored "blob" glows behind it. Google sign-in is
available (web only). Role-tinted (`accentColor` prop) so the same shell
looks different for Student/Teacher/Admin sign-in.

- Fairly plain form-on-a-card execution — functionally complete but no
  illustration, no per-step visual distinction between Login vs. Register vs.
  2FA setup beyond the heading text. 2FA setup in particular (scanning a QR
  code into an authenticator app) is a moment that could use more visual
  guidance/reassurance for a school-age or first-time-2FA user.
- Admin is login-only (no register screen reachable) — make sure any redesign
  of the "switch to register" link correctly hides/disables for that role.

### 4.3 Dashboards (`src/screens/dashboard/*`, shell: `DashboardShell.tsx`)

Three real, data-backed dashboards sharing one shell (header with brand
mark + user identity + sign-out) and one `DashboardCard` component (frosted
glass, used for every list/form section):

- **Student** — see assignments for their class, submit against one (see
  gap below), view their own graded scores, call their teacher.
- **Teacher** — create/manage a class, post assignments, review and grade
  submissions, call students.
- **Admin** — manage accounts (reassign role/class), manage classes
  (create/assign teacher/delete).

All three are subtle-gradient background + frosted cards + plain
`sectionTitle`/`listItem` rows — functional, information-dense, but visually
the least differentiated part of the app right now (a list of text rows in a
card, repeated). This is real, live data (Supabase-backed, RLS-scoped), not
placeholder content, so empty/loading/error states matter and currently get
minimal treatment (a single italic "no X yet" line, a plain "Loading..."
line, a red text line for errors).

- **Real gap:** "Submit Recording" for an assignment is currently a **text
  note field standing in for a video upload** — there's no camera-capture UI
  in the dashboard flow yet, even though camera capture logic already exists
  in the translator screens. If/when that gets built, the recording UI has a
  precedent to follow (Section 4.4) rather than inventing a third pattern.
- Score display (`Correct (87%)` as plain text) is a good candidate for a
  more visual treatment — this app's whole premise is a visual/motion
  language (ASL), and score feedback is currently the least visual moment in
  the product.
- Role-based visual differentiation is currently just the header accent
  color — worth considering whether Teacher/Admin (more data-heavy,
  desk-bound use) vs. Student (simpler, possibly more casual use) should
  diverge more in layout density, not just color.

### 4.4 Translator (`src/screens/TranslatorHubScreen.tsx` + `LiveTranslatorScreen.tsx` + `WordTranslatorScreen.tsx`)

The core recognition experience. A pill switcher toggles between:

- **Letters** (`LiveTranslatorScreen`) — single-frame fingerspelling
  recognition, continuous live prediction + confidence, plus a **Left/Right
  signing-hand toggle** (mirrors hand landmarks for left-handed signers —
  new this session, minimally styled as a small text+pill control).
- **Words** (`WordTranslatorScreen`) — record-a-clip → classify → ranked
  top-5 word predictions → auto-translate/speak in a chosen language. Desktop
  layout was just reworked to a wide two-pane split: predictions on the
  left, a large (up to 960px) camera panel on the right, replacing an
  earlier narrow centered-column layout.

Both are still explicitly labeled internally as **"(Web Test)"** — they're
functionally complete but were built/iterated as engineering test harnesses
first, polish second. This is probably the **single highest-value area for a
design pass**, since it's the product's core differentiator:

- The prediction list (word + confidence %) is plain text rows — an obvious
  candidate for real data visualization (confidence bars, animated reveal on
  a new top prediction, etc.).
- No onboarding/first-run guidance anywhere — a first-time user lands
  straight on a live webcam with a "Record a sign" button and no explanation
  of what's about to happen, what a good recording looks like, or what the
  confidence score means.
- Recording state feedback is minimal (a red dot + frame count badge).
- The handedness toggle is new and easy to miss — small text label, no icon,
  no first-run callout, despite solving a real accessibility problem (the
  model was trained right-hand-dominant, so left-handed signers get
  meaningfully worse recognition without it).
- Error states (model load failure, camera permission denied, translation
  API failure) surface as small plain-text status lines, not a designed
  error state.

### 4.5 Video Call (`src/screens/videocall/VideoCallScreen.tsx`)

Real peer-to-peer WebRTC calling (Student ↔ Teacher), with **live sign-
recognition captions overlaid on both the local and remote video feeds
independently** — genuinely the most technically distinctive screen in the
app. Currently styled as a **flat dark call UI** (near-black background,
white captions, a small picture-in-picture self-view) and was **explicitly
not touched** by this session's glassmorphism pass.

- This was a deliberate scope decision (video-calling UIs conventionally
  stay dark/neutral so the video content itself isn't competing with chrome
  — think Zoom/Meet/FaceTime), but it does mean this screen now looks
  visually disconnected from the rest of the app. Worth an explicit design
  decision: keep it intentionally distinct (dark/focused "call mode," common
  and reasonable), or bring it into the same visual language at least for
  the surrounding chrome (incoming-call card, controls) while leaving the
  video tiles themselves neutral.
- Caption styling (bottom-anchored semi-transparent bar) is minimal —
  captions are core to this screen's whole value proposition and could
  carry more visual weight/polish.

### 4.6 Not in scope for a visual pass

`TestModelScreen.tsx` is an orphaned internal dev harness (not reachable from
any real navigation flow) — skip it.

## 6. Known gaps & opportunities (prioritized, not exhaustive)

Roughly highest-leverage first:

1. **Accessibility audit.** This is a DHH-facing product and has not had a
   dedicated accessibility pass: no systematic contrast audit (spot-checked
   informally during the glassmorphism build, not verified against WCAG),
   no screen-reader label audit, no keyboard-navigation audit beyond focus
   rings on a few components, no captions/motion-reduction consideration.
   Given the audience, this arguably belongs above visual polish.
2. **Translator screen polish** (Section 4.4) — the core product experience
   is still visually the least finished, most "engineering test harness"
   part of the app.
3. **Unify the two glass-tint treatments** (sheer vs. frosted, currently two
   separately-defined constants in different files) into one configurable
   `GlassCard` prop, and consider whether `GlassCard`/`GradientBackground`
   should be the actual source of truth `Design` iterates on, vs. designing
   in isolation and handing off values to re-implement.
4. **Dashboard visual differentiation** (Section 4.3) — currently the most
   repetitive part of the app (plain list-in-a-card, three times over).
5. **Logo/brand mark maturity** (Section 4.1) — the hand-skeleton mark is
   functional but has never had a real design pass despite being the most-
   repeated brand element in the app.
6. **No dark/light mode choice.** The whole app is currently one fixed,
   fairly saturated dark-gradient-leaning look. Worth considering whether a
   lighter/higher-contrast mode matters for a school context (bright
   classroom lighting, projector use, younger students, low-vision users).
7. **Mobile is currently the secondary target.** Recent redesign attention
   (Role Select split-pane, Word Translator big-camera layout) went to
   desktop first; mobile layouts are simpler stacked fallbacks, not a full
   mobile-first pass.
8. **Empty/loading/error states are minimal everywhere** — a single italic
   line or plain red text, no designed empty-state illustrations, skeleton
   loaders, or toast/banner system.
9. **No onboarding/first-run experience** anywhere in the app, most notably
   on the translator screens where it would matter most.
10. **Type scale isn't formalized** — font sizes are picked per-screen
    rather than drawn from a shared scale (e.g. `h1/h2/body/caption`
    tokens). Low effort, would pay off across every future screen.

## 7. Open questions for Design (need a decision, not just execution)

- Should Video Call (Section 4.5) join the glassmorphism visual language, or
  stay intentionally distinct as a focused "call mode"?
- Is Violet Dusk the final palette, or still open? (Two other fully-designed
  alternatives exist — see Section 5.)
- Does this product need a light mode, or is the current dark-leaning
  gradient identity intentional and final?
- Should the 4-cards-including-Translator pattern on Role Select
  (Section 4.1) change, given "skip login entirely" is a different kind of
  action than "sign in as a role"?
- How much of the confidence/prediction UI (Section 4.4) is worth animating
  vs. keeping simple for a school demo/classroom context where predictability
  might matter more than delight?
